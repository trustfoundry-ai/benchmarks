# `trustfoundry-legal-search` adapter

Wraps TrustFoundry's public search API. It is the canonical baseline for the [`trustfoundry-legal-search`](../../suites/trustfoundry-legal-search/README.md) benchmark (model types `case_question`, `case_key_fact`, `law_question`, `reg_question`) and, driven with `model_type: case_name`, for the [`trustfoundry-case-name-lookup`](../../suites/trustfoundry-case-name-lookup/README.md) benchmark — see ["Trustfoundry-case-name-lookup lane"](#trustfoundry-case-name-lookup-lane-model_type-case_name) below. Every published result bundle under [`results/trustfoundry-legal-search/`](../../results/trustfoundry-legal-search/) was generated by this adapter.

## Integration approach

- Each benchmark row's `query_text` is sent as a single `POST` to `https://api.trustfoundry.ai/public/v1/search`.
- The row's `model_type` (`case_question`, `case_key_fact`, `law_question`, or `reg_question`) is forwarded on the request body so the same generic provider config works for all four benchmark targets.
- The row's `geo_level_1_identifier` (US state or `FED`) is forwarded as the `state` filter, so search results are scoped to the row's jurisdiction — the same shape the `courtlistener-search` adapter mirrors via CL's `court=` param.
- The scorer matches on the TrustFoundry `document_uuid` the API returns for each result (native ID join), falling back to citation string matching if the ID is missing.

## Retry semantics

The adapter makes **one** retry for transient provider failures:
- Network fetch errors
- Streamed provider error events
- Missing-result events
- HTTP 5xx responses

It does **not** retry:
- Validation errors (row-shape issues)
- HTTP 4xx responses (auth, rate limits, malformed requests)

On a successful retry the row is scored from the successful response and latency includes the full elapsed time across both attempts. On a persistent failure the row surfaces as `provider_failure` in the scored output.

## Run

**Prerequisites:**
- `TF_API_KEY` in your environment (create from your TrustFoundry account dashboard):
  ```bash
  export TF_API_KEY=your_key_here
  ```
- `pnpm install` at the repo root.

**Command** (200 case-question rows, deterministic first-N slice of the 5k dataset):

```bash
pnpm benchmark run \
  --benchmark-config configs/benchmarks/trustfoundry-legal-search/case-questions-200.json \
  --provider-config configs/providers/trustfoundry-legal-search.json \
  --out runs/trustfoundry-legal-search-case-questions-200 \
  --parallel 8 \
  --force
```

**Full 5k run:**

```bash
pnpm benchmark run \
  --benchmark-config configs/benchmarks/trustfoundry-legal-search/case-questions-5k.json \
  --provider-config configs/providers/trustfoundry-legal-search.json \
  --out runs/trustfoundry-legal-search-case-questions-5k \
  --parallel 8 \
  --force
```

Swap `case-questions` for `key-facts`, `laws`, or `regs` in both the config path and the `--out` directory to run the other three targets. Use `--limit N` / `--offset K` for arbitrary subsets. The generic [`configs/providers/trustfoundry-legal-search.json`](../../configs/providers/trustfoundry-legal-search.json) omits `model_type` and reads each row's value, so one provider config covers all four targets.

## Publishing a result bundle

Turn a run into a checksummed, shareable bundle:

```bash
pnpm benchmark publish-result \
  --run runs/trustfoundry-legal-search-case-questions-200 \
  --out results/trustfoundry-legal-search/<date>/case-questions-200 \
  --force

pnpm benchmark verify-result results/trustfoundry-legal-search/<date>/case-questions-200
```

The published bundle contains `manifest.json` (pins harness commit, config hashes, dataset provenance), `checksums.txt`, `raw.jsonl` (row-level evidence), and `result.json` (aggregate scores). External readers can `pnpm benchmark verify-result <bundle>` to confirm the bundle is intact.

## Trustfoundry-case-name-lookup lane (`model_type: case_name`)

The same provider adapter and endpoint back the [`trustfoundry-case-name-lookup`](../../suites/trustfoundry-case-name-lookup/README.md) benchmark. Here the query *is* a case name — accurate, mangled, abbreviated, reordered, or reduced to a single party — rather than a question, and the lane returns a ranked, deduplicated page of the closest-matching case names rather than a single best answer.

- Every benchmark row's `query_text` (the case-name query, verbatim) is sent as a single `POST` to the same `https://api.trustfoundry.ai/public/v1/search` endpoint.
- `model_type` is pinned to `case_name` in the provider config — [`configs/providers/trustfoundry-case-name-lookup.json`](../../configs/providers/trustfoundry-case-name-lookup.json) — rather than read per-row, because every row in both trustfoundry-case-name-lookup datasets is a case-name query.
- The row's jurisdiction is forwarded as the `state` filter, resolved to `FED` for a federal row. In this suite's data shape that value lives in `geo_level_2_identifier`, not `geo_level_1_identifier` — `geo_level_1_identifier` is always the literal `us` here, unlike the four question-shaped targets where it directly carries the state or `FED`. `state` is required: the API rejects a `case_name` request with no jurisdiction, exactly as it does for the four question-shaped model types.
- Scoring is caption-based, not citation- or UUID-based — see the suite README's ["Matching rule"](../../suites/trustfoundry-case-name-lookup/README.md#matching-rule-equality-except-one-category). The [`trustfoundry-case-name-lookup`](../../src/adapters/scorers/trustfoundry-case-name-lookup.mjs) scorer does the matching, not the `trustfoundry-legal-search` scorer.
- Retry semantics are identical to the rest of this adapter — see ["Retry semantics"](#retry-semantics) above.

### Run

**Prerequisites:** same as above — `TF_API_KEY` in your environment, `pnpm install` at the repo root.

Both datasets are needed to read the suite: the public set carries the recall number and the negatives set carries the false-positive rate that prices it.

```bash
export TF_API_KEY=your_key_here

pnpm benchmark run \
  --benchmark-config configs/benchmarks/trustfoundry-case-name-lookup/v2-public.json \
  --provider-config  configs/providers/trustfoundry-case-name-lookup.json \
  --scorer-config    configs/scorers/trustfoundry-case-name-lookup.json \
  --out runs/v2-public --parallel 4 --retries 2

pnpm benchmark run \
  --benchmark-config configs/benchmarks/trustfoundry-case-name-lookup/v2-negatives.json \
  --provider-config  configs/providers/trustfoundry-case-name-lookup.json \
  --scorer-config    configs/scorers/trustfoundry-case-name-lookup.json \
  --out runs/v2-negatives --parallel 4 --retries 2
```

Use `--limit N --offset K` for a smaller smoke; this suite has no separate 200-row companion config the way the four question-shaped targets do.

### Publishing a result bundle

```bash
pnpm benchmark publish-result --run runs/v2-public --out results/trustfoundry-case-name-lookup/<date>/public-8850 --force
pnpm benchmark publish-result --run runs/v2-negatives --out results/trustfoundry-case-name-lookup/<date>/negatives-50 --force

pnpm benchmark verify-result results/trustfoundry-case-name-lookup/<date>/public-8850
pnpm benchmark verify-result results/trustfoundry-case-name-lookup/<date>/negatives-50
```

Case-name gold does not fit the raw-row schema's default `expected` shape, which is built for single-citation gold. The `trustfoundry-case-name-lookup` benchmark adapter declares `publishedExpectedFields` so its caption-based gold survives publishing and re-scoring — see [`results/README.md`](../../results/README.md#suites-whose-gold-does-not-fit-the-default-raw-row-shape).

### What to expect

The public set (8,850 rows) took 1019 s wall-clock (8.68 rows/s) at 4 concurrent
requests (`--parallel 4`): latency p50 406 ms, p95 511 ms, mean 429 ms. The negatives
set (50 rows) finishes as a run in about 8 s wall-clock at the same concurrency, but
its per-request tail is not near-instant: p50 321 ms, p95 1038 ms, mean 598 ms.

## Request limit and scorer cutoffs

Both knobs live in [`configs/scorers/trustfoundry-legal-search.json`](../../configs/scorers/trustfoundry-legal-search.json):

| Field | Purpose |
| --- | --- |
| `api_request_limit` | Number of results requested per `/public/v1/search` call (forwarded as `limit` in the request body). |
| `cutoffs` | List of K values for `hits@K` reported in the scores file. |
| `headline_cutoff` | The featured `hits@K` shown in the run summary. |

**Public API cap.** `api_request_limit` must align with the caller-facing cap enforced by <https://api.trustfoundry.ai>. The current cap is 25; raising it past that causes every call to fail with HTTP 400.

**Startup validation.** The runner refuses to start unless:

1. `api_request_limit >= max(cutoffs + headline_cutoff)` — otherwise `hits@K` for K > `api_request_limit` is meaningless (the API would never return enough results to hit it).
2. `cutoffs` and `headline_cutoff` match the values the `trustfoundry-legal-search` scorer is actually computing. The published result-bundle schema currently pins `hits@K` to `K in {1, 5, 10, 25}`; changing that requires updating both [`src/adapters/scorers/trustfoundry-legal-search.mjs`](../../src/adapters/scorers/trustfoundry-legal-search.mjs) and the artifact schema together.

Each validation error names both numbers and points back to the API URL. Individual provider configs can still pin an explicit `limit` if an adapter needs different semantics; the explicit value wins over the scorer-driven default.
