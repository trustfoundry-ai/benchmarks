# `trustfoundry-legal-search` adapter

Wraps TrustFoundry's public search API — the canonical baseline for the [`trustfoundry-legal-search`](../../suites/trustfoundry-legal-search/README.md) benchmark. Every published result bundle in [`results/trustfoundry-legal-search/`](../../results/trustfoundry-legal-search/) was generated by this adapter.

## Integration approach

- Each benchmark row's `query_text` is sent as a single `POST` to `https://api.trustfoundry.ai/public/v1/search`.
- The row's `model_type` (`case_question`, `case_key_fact`, `law_question`, or `reg_question`) is forwarded on the request body so the same generic provider config works for all four benchmark targets.
- The row's `geo_level_1_identifier` (US state or `FED`) is forwarded as the `state` filter, so search results are scoped to the row's jurisdiction — the same shape the `courtlistener-search` adapter mirrors via CL's `court=` param.
- The scorer matches on the TrustFoundry `document_uuid` the API returns for each result (native ID join), falling back to citation string matching if the ID is missing.

## Retry semantics

The adapter makes **one** retry for transient provider failures:
- Network fetch errors
- Streamed provider error events
- Missing-result events
- HTTP 5xx responses

It does **not** retry:
- Validation errors (row-shape issues)
- HTTP 4xx responses (auth, rate limits, malformed requests)

On a successful retry the row is scored from the successful response and latency includes the full elapsed time across both attempts. On a persistent failure the row surfaces as `provider_failure` in the scored output.

## Run

**Prerequisites:**
- `TF_API_KEY` in your environment (create from your TrustFoundry account dashboard):
  ```bash
  export TF_API_KEY=your_key_here
  ```
- `pnpm install` at the repo root.

**Command** (200 case-question rows, deterministic first-N slice of the 5k dataset):

```bash
pnpm benchmark run \
  --benchmark-config configs/benchmarks/trustfoundry-legal-search/case-questions-200.json \
  --provider-config configs/providers/trustfoundry-legal-search.json \
  --out runs/trustfoundry-legal-search-case-questions-200 \
  --parallel 8 \
  --force
```

**Full 5k run:**

```bash
pnpm benchmark run \
  --benchmark-config configs/benchmarks/trustfoundry-legal-search/case-questions-5k.json \
  --provider-config configs/providers/trustfoundry-legal-search.json \
  --out runs/trustfoundry-legal-search-case-questions-5k \
  --parallel 8 \
  --force
```

Swap `case-questions` for `key-facts`, `laws`, or `regs` in both the config path and the `--out` directory to run the other three targets. Use `--limit N` / `--offset K` for arbitrary subsets. The generic [`configs/providers/trustfoundry-legal-search.json`](../../configs/providers/trustfoundry-legal-search.json) omits `model_type` and reads each row's value, so one provider config covers all four targets.

## Publishing a result bundle

Turn a run into a checksummed, shareable bundle:

```bash
pnpm benchmark publish-result \
  --run runs/trustfoundry-legal-search-case-questions-200 \
  --out results/trustfoundry-legal-search/<date>/case-questions/200 \
  --force

pnpm benchmark verify-result results/trustfoundry-legal-search/<date>/case-questions/200
```

The published bundle contains `manifest.json` (pins harness commit, config hashes, dataset provenance), `checksums.txt`, `raw.jsonl` (row-level evidence), and `result.json` (aggregate scores). External readers can `pnpm benchmark verify-result <bundle>` to confirm the bundle is intact.

## Request limit and scorer cutoffs

Both knobs live in [`configs/scorers/trustfoundry-legal-search.json`](../../configs/scorers/trustfoundry-legal-search.json):

| Field | Purpose |
| --- | --- |
| `api_request_limit` | Number of results requested per `/public/v1/search` call (forwarded as `limit` in the request body). |
| `cutoffs` | List of K values for `hits@K` reported in the scores file. |
| `headline_cutoff` | The featured `hits@K` shown in the run summary. |

**Public API cap.** `api_request_limit` must align with the caller-facing cap enforced by <https://api.trustfoundry.ai>. The current cap is 25; raising it past that causes every call to fail with HTTP 400.

**Startup validation.** The runner refuses to start unless:

1. `api_request_limit >= max(cutoffs + headline_cutoff)` — otherwise `hits@K` for K > `api_request_limit` is meaningless (the API would never return enough results to hit it).
2. `cutoffs` and `headline_cutoff` match the values the `trustfoundry-legal-search` scorer is actually computing. The published result-bundle schema currently pins `hits@K` to `K in {1, 5, 10, 25}`; changing that requires updating both [`src/adapters/scorers/trustfoundry-legal-search.mjs`](../../src/adapters/scorers/trustfoundry-legal-search.mjs) and the artifact schema together.

Each validation error names both numbers and points back to the API URL. Individual provider configs can still pin an explicit `limit` if an adapter needs different semantics; the explicit value wins over the scorer-driven default.
